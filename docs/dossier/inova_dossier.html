1. Résumé

INOVA aide un pentesteur à exploiter un modèle d'IA pendant un test d'intrusion sans exposer les données du client et sans laisser l'IA agir seule.

La plateforme enchaîne sept phases, de la configuration au rapport. Les outils de sécurité classiques (nmap, nuclei) détectent les services et les vulnérabilités ; l'IA analyse, priorise, cherche des enchaînements entre failles et rédige. Deux mécanismes encadrent cette IA :

  • La maîtrise des données. Un aiguilleur décide, avant la mission, si le raisonnement se fait sur un petit modèle local (SLM) ou sur un grand modèle externe (LLM cloud). Sur la route cloud, une passerelle fondée sur Microsoft Presidio remplace chaque valeur sensible par un jeton ([HOSTNAME_1], [SECRET_2]…) avant tout envoi, puis réinjecte les vraies valeurs dans la réponse, sur la machine. En cas de doute, rien ne sort (principe fail-closed).
  • La maîtrise des actions. Le texte de l'IA est un conseil, jamais une commande. Les seules actions exécutables sont construites par le code, restent dans le périmètre du mandat, sont non destructives et exigent une validation humaine.

Résultats obtenus à ce jour :

  • 0 % de fuite effective sur les 67 valeurs sensibles des cas standard d'un corpus de 56 cas (modèle fr_core_news_md) ;
  • aucune valeur réelle retrouvée dans les envois au cloud lors des missions réelles (contrôle automatique de l'outbox) ;
  • un coût cloud de 0,0003 à 0,005 $ par mission avec Claude Haiku 5.5 ;
  • une chaîne complète validée sur un laboratoire réel (OWASP Juice Shop et applications Vulhub) ;
  • 52 tests automatisés.

2. Contexte et problématique

2.1 Le constat

Les grands modèles de langage savent déjà assister un test d'intrusion : interpréter la sortie d'un scanner, relier deux failles, proposer une vérification ou rédiger un rapport. Les travaux de recherche sur PentestGPT (arXiv 2308.06782) montrent qu'un LLM améliore nettement la progression d'un testeur, mais qu'il perd le fil sur les tâches longues et que les petits modèles raisonnent moins bien que les grands.

Dans une entreprise comme un assureur, deux obstacles empêchent pourtant d'envoyer un pentest à un modèle externe :

  1. Les données. Un pentest manipule des adresses IP internes, des noms de serveurs, des identifiants, des extraits de bases de données, parfois des données personnelles de clients. Les envoyer à un fournisseur externe est incompatible avec la confidentialité attendue, le RGPD et la loi marocaine 09-08.
  2. Les actions. Un modèle peut proposer une commande destructive, viser une machine hors du mandat, ou être manipulé par un texte piégé caché dans la cible (injection de prompt).

2.2 La problématique

Problématique. Comment bénéficier des capacités des modèles IA pour réaliser des tests d'intrusion, tout en maîtrisant les données auxquelles ils ont accès et les actions qu'ils peuvent proposer ?

2.3 Les options étudiées

OptionPrincipeLimite principale
Tout en local (SLM)Un petit modèle tourne sur la machine du pentesteur : rien ne sort.Qualité de raisonnement nettement inférieure (constaté en mission, voir §20.3).
Tout au cloud, sans protectionLe grand modèle reçoit les données brutes.Inacceptable pour des données client.
LiteLLM + PresidioAccès unifié aux modèles et anonymisation par détection d'entités.Presidio ne connaît pas les données d'un pentest (IP, secrets, URL…) : il faut l'étendre.

DontFeedTheAIMasquage de données sensibles avant un LLM.Pas de décision local / cloud ni de contrôle des actions.

2.4 La solution retenue

Une architecture hybride avec aiguillage : le modèle local décide du chemin selon deux critères (complexité du pentest et sensibilité des données). Les pentests simples restent en local. Les pentests lourds partent au cloud à travers la passerelle de masquage. Les pentests lourds sur des données trop sensibles restent en local, avec une validation humaine renforcée. Tout le système est fail-closed : en cas de doute, la donnée ne sort pas.

5. Architecture générale

Tout s'exécute sur la machine du pentesteur, sauf l'appel au LLM cloud. La frontière entre les deux est le cœur du projet : seul du texte masqué la franchit, et la table qui permet de retrouver les vraies valeurs ne la franchit jamais.

Figure 1 : architecture hybride. Le trait rouge est la frontière : seuls des jetons la franchissent.

5.1 Les trois routes

RouteQuandOù raisonne l'IACe qui sort
LOCALPentest simpleSLM local, données réellesRien
CLOUDPentest lourd, données peu sensiblesLLM cloud pour les étapes autorisées (analyse, rapport), SLM local pour le resteTexte masqué uniquement
LOCAL_RESTRICTEDPentest lourd, données très sensiblesSLM local, validation humaine renforcéeRien

5.2 Principes de conception

  1. Fail-closed : tout doute (détection incertaine, fuite résiduelle, plafond atteint, cloud indisponible) se règle en restant local.
  2. Le code agit, l'IA conseille : aucune commande n'est tirée d'une réponse de l'IA.
  3. Masquer les valeurs, garder la structure : un même hôte garde le même jeton partout, pour que l'IA puisse relier les failles.
  4. Tout est mesuré : chaque appel, chaque envoi, chaque décision est journalisé et vérifiable après coup.
  5. Défense en profondeur : chaque risque est couvert par plusieurs mécanismes indépendants.

7. L'aiguilleur : local ou cloud

L'aiguilleur répond à deux questions, dans cet ordre : le modèle local en est-il capable ? (complexité) et, sinon, les données peuvent-elles sortir, une fois masquées ? (sensibilité). Les scores sont calculés par des règles explicites, reproductibles et défendables devant un jury. En option, le SLM local peut les affiner : la complexité est alors moyennée, et la sensibilité ne peut qu'augmenter.

Exemple. Un pentest web en boîte grise, authentifié, sur une application sur mesure avec enchaînement de failles, pour un assureur aux données « internes » : complexité 0,40 + 0,15 + 0,15 + 0,25 = 0,95 ; sensibilité 0,40 + 0,10 + 0,05 = 0,55. Le pentest est lourd et les données peuvent sortir masquées : route CLOUD. La même mission classée « secret » donne une sensibilité de 1,0 : route LOCAL_RESTRICTED.

8. La passerelle de confidentialité

La passerelle est le seul chemin vers le cloud. Elle s'appuie sur Microsoft Presidio (détection d'entités par motifs et par modèle de langue spaCy), étendu aux données propres à un pentest.

Figure 4 : traitement d'un texte sur la route cloud.

8.1 Ce qui est détecté

EntitéExemples de formats reconnus
Adresses IP de la cibleIPv4, IPv4 « neutralisée » 10[.]10[.]0[.]5 ; contrôle supplémentaire des IP du périmètre
URL et noms d'hôteshttp(s)://…, hxxp://…, noms de domaine complets, domaines neutralisés
SecretsPaires clé/valeur (.env, JSON, YAML), define() PHP, identifiants dans une URI, en-têtes Basic et Bearer, JWT, clés AWS, blocs de clé privée entiers
EmpreintesHachages de mots de passe
Objets de base de donnéesRequêtes SQL, sorties sqlmap (Database:, Table:)
Données personnellesNoms de personnes (spaCy), adresses postales, CIN marocaine (confirmée par le contexte), téléphones FR/MA/BE/CH/US/GB, cartes bancaires, IBAN dont marocain
Termes du clientNom du client et termes sensibles déclarés dans le périmètre (liste de refus, score forcé à 0,9)

Une liste blanche protège le vocabulaire utile au raisonnement (CVE, CVSS, EPSS, Apache, PHP, SQL, RCE…), et un filtre écarte les faux noms de personnes (identifiants techniques contenant des chiffres ou des tirets).

8.2 Comment c'est masqué

  • Jetons cohérents. Une même valeur reçoit toujours le même jeton ([TARGET_IP_1]) et deux valeurs différentes deux jetons différents : l'IA peut comparer sans connaître.
  • Valeur seule pour les secrets. DB_PASSWORD=S3cr3t! devient DB_PASSWORD=[SECRET_1] : la clé reste lisible et l'IA comprend de quoi il s'agit.
  • Masquage structurel des URL. https://intranet.client.ma/admin devient https://[HOSTNAME_1]/admin : l'hôte garde son jeton partout, le chemin reste lisible, et ce qu'il contient de sensible (identifiants, token=, termes du client) est masqué à son tour. C'est ce qui permet à l'IA de voir que trois failles sont sur le même serveur.
  • Coffre chiffré. La table jeton ↔ valeur est propre à chaque mission, chiffrée sur disque (Fernet, clé INOVA_VAULT_KEY) et jamais journalisée.

8.3 Fail-closed : quand rien ne sort

SituationRéaction
Une détection a un score entre 0,35 et 0,60 (incertaine)Envoi refusé, raisonnement en local (max_uncertain_spans: 0)
Après masquage, une IP du périmètre, un domaine, un terme sensible ou un motif de secret subsisteEnvoi refusé, raisonnement en local
Un appel cloud avec un texte qui ne vient pas de la passerelleRefus par le code (UnsafePromptError)
Plafond de mission atteintPlus aucun envoi, raisonnement en local
Cloud trop lent ou indisponibleUn nouvel essai, puis raisonnement en local ; l'envoi tenté reste consigné

8.4 Le verrou SafePrompt et le contrôle de l'outbox

Le client LLM n'accepte vers le cloud qu'un objet SafePrompt émis par la passerelle : il est impossible, dans le code, d'envoyer du texte brut par erreur. Chaque texte envoyé est copié dans cloud_outbox.jsonl. En fin de mission, INOVA y cherche toutes les valeurs réelles masquées pendant la mission, les domaines et termes sensibles, les IP du périmètre et les secrets du laboratoire listés dans config/secrets_labo.txt. Le résultat, « aucune valeur sortie » ou la liste des fuites, figure dans le rapport : c'est une mesure, pas une promesse.

9. Le contrôle des actions

La seconde moitié de la problématique porte sur les actions que l'IA peut proposer. INOVA les encadre par cinq mécanismes indépendants.

9.1 Le périmètre (ScopeGuard)

  • Le mandat doit être en cours de validité (dates de début et de fin).
  • Une cible doit appartenir aux domaines ou aux plages IP autorisés ; une plage CIDR doit y être entièrement incluse (un /16 est refusé si le mandat couvre un /24).
  • Les hôtes exclus sont refusés et passés à nmap avec --exclude.
  • Pour un scan de plusieurs cibles, chacune est vérifiée ; une seule hors périmètre bloque tout.

9.2 Les outils

  • Liste blanche : nmap, whatweb, nuclei. Tout autre outil est refusé.
  • Commandes construites par le code à partir de modèles fixes, lancées sans shell (pas d'injection de commande possible).
  • Mode dry_run : les commandes sont affichées sans être exécutées.
  • nuclei toujours lancé avec -ni (pas d'Interactsh : la cible ne contacte jamais de serveur public tiers) et -etags dos,intrusive,fuzz (aucun test destructif).
  • Délai maximal par outil (15 minutes), code retour et journal complet enregistrés.

9.3 La défense contre l'injection de prompt

Les sorties des outils contiennent du texte écrit par la cible. INOVA :

  1. les encadre comme <<<DONNEES_NON_FIABLES source=…>>>, avec une règle système interdisant d'en suivre les instructions ;
  2. y détecte six familles d'injection, en français et en anglais : ignorer les instructions, changement de rôle, faux message système, demande d'exécution, exfiltration, révélation du prompt ;
  3. retire la ligne suspecte avant tout envoi, à un modèle local comme au cloud, et journalise l'évènement.

9.4 La revue des réponses de l'IA

Chaque réponse est relue. Sept familles de propositions dangereuses sont signalées : suppression massive, shell distant, téléchargement puis exécution, PowerShell encodé, destruction de données, déni de service, persistance. Tout hôte cité hors du périmètre est aussi signalé. Rien n'est exécuté : ces alertes informent l'humain et figurent dans le rapport.

9.5 La validation humaine

La seule action exécutable est retest_template : un re-test ciblé d'un test déjà détecté par nuclei (nuclei -id <test>), depuis la racine du site, dans le périmètre. Avant chaque re-test, l'interface affiche une carte « Validation humaine requise » avec l'action exacte. Le pentesteur autorise ou refuse ; sans réponse sous 15 minutes, c'est un refus. Chaque décision est enregistrée avec son auteur.

Défense en profondeur. Une instruction piégée doit franchir la détection, la règle système, la revue des réponses, l'absence d'exécution du texte de l'IA, la liste blanche, le périmètre et la validation humaine. Aucun mécanisme n'est supposé parfait ; c'est leur empilement qui protège.

10. Priorisation des vulnérabilités

Plutôt qu'une formule pondérée difficile à justifier, INOVA suit un arbre de décision inspiré de SSVC (Stakeholder-Specific Vulnerability Categorization), avec trois questions :

11. Pilotage, coûts et robustesse

11.1 Accès aux modèles

LiteLLM offre une interface unique vers le SLM local (Ollama) et vers le fournisseur cloud. Chaque modèle a son mode : mock (simulé, sans clé ni Internet) ou live. Les paramètres refusés par un modèle sont ignorés (drop_params), la télémétrie de LiteLLM est coupée et la grille de prix est lue localement.

11.2 Plafonds de mission

Au-delà de 20 appels cloud, 200 000 tokens ou 60 minutes, plus rien ne part au cloud : la mission continue en local. Ces plafonds protègent le budget et limitent l'exposition.

11.3 Mesure

Chaque appel est enregistré dans usage.jsonl : phase, cible (local ou cloud), modèle, tokens envoyés et reçus, durée, coût calculé d'après les tarifs saisis. Le rapport affiche aussi la durée de chaque phase, utile à l'analyse ROI.

Chaque mission crée un dossier runs/<engagement>_<date>/ :

Ce qui est parti au cloud est uniquement dans cloud_outbox.jsonl, sous forme masquée. Les textes réels échangés avec l'IA sont conservés sur la machine dans mission.json, pour l'historique de l'interface locale. La table de correspondance reste dans .inova_vault/, chiffrée. Les dossiers runs/ et .inova_vault/, le fichier .env, le périmètre réel et les secrets du laboratoire sont exclus du dépôt git.

13. Interface web

L'interface, aux couleurs d'AXA, est servie par un petit serveur Python intégré (bibliothèque standard), lancé par python -m inova.main web. Elle n'écoute que sur 127.0.0.1 : elle peut donc afficher les valeurs réelles et la table de correspondance, qui ne quittent pas la machine.

OngletContenu
Tableau de bord« La frontière » : raisonnements locaux, valeurs remplacées, replis, pièges neutralisés, envois masqués, valeurs réelles reçues par le cloud (0). Constats des dernières missions par gravité, routes choisies, coût cumulé, durée médiane, tokens.
1. PérimètreSaisie et validation du mandat, des cibles et de la classification.
2. AiguillageSimulateur : carte complexité × sensibilité avec un point qui se déplace selon le profil, scores et raisons.
3. PasserelleDémonstration sur un texte libre : entités détectées, texte envoyé, réponse brute, réponse réinjectée, table de correspondance, verdict.
4. MissionLancement (démo ou outils réels, classification, type), frise des 7 phases en direct, cartes de validation, frontière propre à la mission, constats par application, services, échanges avec l'IA.
5. RapportVersion technique ou direction, export PDF de qualité impression.
HistoriqueToutes les missions enregistrées, réouvrables.
Taux de fuiteLancement de l'évaluation de la passerelle et lecture des indicateurs.

Sécurité de l'interface

  • Écoute locale uniquement ; contrôle de l'en-tête Origin sur les requêtes d'API.
  • Politique de sécurité du contenu (CSP) stricte ; aucune ressource externe : les polices sont fournies avec l'application.
  • Taille des requêtes limitée ; noms de mission contrôlés (pas de traversée de répertoire).
  • Une seule mission à la fois ; reprise du suivi après rechargement de la page.

20. Résultats et évaluation

20.1 Taux de fuite de la passerelle

Corpus de 56 cas fictifs (84 valeurs sensibles, 41 éléments à préserver) : sorties nmap, nuclei, sqlmap, en-têtes HTTP, JSON, fichiers de configuration, journaux, texte libre en français, obfuscations. 13 cas sont marqués difficiles a priori.

ItérationModèle FRFuite effective standardCas difficilesGlobalReplisSur-masquage

2. détecteurs amélioréssm3,0 % (2/67)29,4 %8,3 %0,0 %0,0 %
2. détecteurs améliorésmd0,0 % (0/67)29,4 %6,0 %0,0 %0,0 %

La fuite effective compte les valeurs qui seraient réellement sorties : présentes après masquage dans un texte que la passerelle a accepté d'envoyer. C'est l'indicateur de confidentialité.

Mise en garde. Les détecteurs de l'itération 2 ont été conçus après avoir vu les échecs de l'itération 1, par la même personne qui a écrit le corpus. Le 0 % mesure la couverture des formats connus et surestime probablement la performance sur des données inédites. Un jeu de test indépendant, issu du laboratoire et jamais utilisé pour régler les détecteurs, est prévu.

20.3 Local contre cloud

Sur la même mission, le petit modèle local (3 milliards de paramètres) garantit l'absence de toute sortie mais commet des erreurs que le grand modèle ne fait pas : définition inventée d'EPSS, correctif erroné (PHP 8.2.5, encore vulnérable à CVE-2024-4577), action offensive rangée dans la remédiation, enchaînements faibles, conclusions contradictoires. Cela confirme le constat de PentestGPT et justifie l'aiguillage : le cloud masqué pour la qualité, le local pour les données les plus sensibles, avec une validation humaine renforcée.

20.4 Couverture de détection

Sur Juice Shop, qui contient plus de 100 failles volontaires, surtout logiques, nuclei n'en a détecté qu'une. Les scanners à signatures trouvent les CVE et erreurs de configuration connues, pas les failles de logique applicative. L'IA ne voit que ce que les outils trouvent : INOVA assiste le pentesteur, il ne le remplace pas.
